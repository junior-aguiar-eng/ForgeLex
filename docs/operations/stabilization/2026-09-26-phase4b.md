## Gate de segurança encontrado

Em consulta read-only ao PostgreSQL do Supabase produtivo, as 46 tabelas de
`public` possuíam `SELECT` para `anon` e `authenticated` sem RLS; a amostra de
contas/billing também concedia escrita. O teste
HTTP com `limit=0` retornou `503 PGRST002`; não demonstrou acesso efetivo a
linhas. Boni autorizou a correção. A migration
`ops/gcp/production/supabase-public-access-hardening.sql` foi testada em
PostgreSQL 16 local com tabela e ACLs sintéticas. A primeira tentativa remota
falhou ao alterar privilégios padrão de `supabase_admin`, que não é administrado
pelo usuário `postgres`; a transação foi revertida e o estado de 46/0/46 foi
confirmado novamente. A migration ajustada foi aplicada com sucesso ao projeto
`mmywgqttfthtwntjkqgh`. Verificação posterior: **46/46 tabelas com RLS,
0/46 com SELECT para `anon`, 0/46 para `authenticated`, 46/46 com SELECT para
`service_role` e nenhuma sequência com USAGE para `anon`**. Os privilégios
padrão de `postgres` foram retirados dessas duas roles. Os privilégios padrão
de `supabase_admin` persistem, pois a conexão não pode alterá-los; novos objetos
criados por essa role exigem verificação. O advisor agora informa 46 tabelas
com RLS sem políticas, esperado para o acesso exclusivo pelo backend, e mantém
o aviso de proteção contra senhas vazadas desabilitada. Nenhuma linha de usuário
foi consultada. A saúde de Auth sem `apikey` respondeu 401, portanto a validação
autenticada de Auth continua pendente.
